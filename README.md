# 求职自动化工作流

> 把「找工作」做成一条日更无人值守的流水线：三源抓取 → 规则筛 → 双轨打分 → 话术生成 → SQLite 入库 → Flask 看板。单次跑完约 2.5 分钟处理 400+ 岗位。

详细复盘见博客文章：[求职自动化工作流：把找工作做成一条可核验的流水线](https://koujiaohan.github.io/posts/job-autopilot.html)。

## 流水线架构

```
三源抓取 → 规则筛 → 双轨打分 → 话术生成 → SQLite 入库 → Flask 看板
(Playwright)  (硬过滤)  (LLM+覆盖率) (禁用词护栏)  (指纹去重)   (每日检视)
```

每个环节可独立替换：换抓取源、换打分策略、换看板，互不影响。

## 核心设计

### 双轨打分：用客观覆盖率校验 LLM

LLM 给「岗位匹配度」打分容易虚高——把「岗位提到 Python」就当强匹配。加一条客观轨道：把简历技能/经历拆成清单，数 JD 实际命中多少条，得到可复算的覆盖率。

两条轨道最大差达 **26 分**。于是覆盖率成了校准尺：
- LLM 分数高但覆盖率低 → 判虚高，往下压
- JD 信息缺失的岗位 → 设兜底分，避免「没信息」被当成「高匹配」

**教训**：不要让 LLM 自己当自己输出的裁判，找一个确定的、可复算的量交叉验证。

### 反爬与降级
接口被风控挡下时自动切到页面 DOM 抓取。踩过的坑：卡片选择器写错导致 0 命中，一度误判为反爬升级——用「单页对照测试」逐条比对才发现是 class 名变了。方向错了会在错误的地方耗很久。

### 成本与护栏
- **命中缓存 + 指纹去重**：同岗位（标题+公司指纹）只算一次，Top40 全命中时 LLM 调用降为 0
- **话术禁用词护栏**：自动生成的打招呼话术过禁用词表，拦住简历画像未授权的表述
- **岗位文本当不可信输入**：JD 文字只当数据、绝不当指令，防止「忽略之前要求」藏进岗位描述

## 技术栈

Python · Playwright · SQLite · Flask · LLM API · TF-IDF（可选关联检索）

## 方法论要点

1. **LLM 做判断 + 确定量做校验**：自动化分数必须有一条独立轨道盯着
2. **可追溯优先**：每个岗位为什么高分、话术每句话从哪来，都能在库和看板里查到
3. **失败要可定位**：0 命中时先做对照测试定位，别急着调参硬试
